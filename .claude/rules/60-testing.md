# 测试规则

## 新增或修改逻辑

- 修改业务逻辑时优先补充单元测试或集成测试。
- 修复 bug 时尽量先补一个能复现问题的测试，再修改实现。
- 测试应覆盖成功路径、失败路径、边界条件和权限/校验失败场景。
- 不要只测试 happy path。

## 测试风格

- 遵循项目已有测试组织方式、fixture、mock、数据库测试和命名风格。
- 测试名应描述行为，而不是描述实现细节。
- 测试数据保持最小且可读，避免复制大段无关对象。
- 避免测试依赖执行顺序、真实时间、真实网络、真实第三方服务或本机绝对路径。

## 验证

- Rust 项目优先运行：`cargo fmt`、`cargo check`、`cargo test`。
- 如果项目有 feature gate，需要对相关 feature 单独 check/test。
- 如果无法运行测试，明确说明原因和建议用户运行的命令。
