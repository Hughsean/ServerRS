- **协议无关契约**：`personal-secretary` 领域/application 层固定从最新位置向更旧
  消息读取，将原 `Option<BackfillCursor>` 拆为互斥的 `Next`、`ProvenHistoryStart`

- **连续性与边界**：每页在 ingestion 前校验 cursor/scope 账号、信封账号/会话、
  非空锚点、页内唯一性、前页单锚点重叠、Next 真实来源及游标推进，不对 opaque
  `message_seq` 进行数值运算或排序。冻结 boundary 只在统一幂等入口返回
  `Duplicate` 时成立；`Accepted` 记录状态不一致，两者都立即停止页内更旧写入。
- **完整性**：有 boundary 但到达 `ProvenHistoryStart` 仍未命中时保持
  `Unprovable`；无 boundary 时只有起点证据才证明 scope。Fake 同时证明账号会话
  全集才可 `ProvenComplete`，否则最多 `KnownScopesComplete`且 Gap 仍为 `uncertain`。
  空页、`UnprovenStop`、短页本身、预算耗尽与顺序/连续性异常都不推导完整。
- **NapCat/QQBot**：公开历史查询构造改用 `HistoryReadDirection`，OneBot
  `reverseOrder` 映射留在私有 HTTP 实现。群/私聊适配器使用 `TowardOlder`；非空页
  只从真实末锚点构造 `Next`，空页与 OwnerControl 只返回 `UnprovenStop`，短页不证明
  结束，后续请求原样传递 opaque `message_seq`，底层错误不传播账号/会话/锚点/正文/
  Token/URL/响应 data。七项只读 action 白名单未扩展。

## 2026-08-04 18:06（Asia/Shanghai）：EVT-007-MSG 延迟 Reply 子先父后解析闭环

- **范围**：仅 NapCat 群消息与私聊消息的消息 Reply（`ContentSegment::Reply`）。文件、卡片、
  通知等非消息 Reply 拆为 `EVT-007-NONMSG`，待取得真实业务样本后另行设计，本切片未顺带实现。
- **现状复用**：`secretary_source_events.reply_to_platform_event_id` 已随子 SourceEvent 同一
  事务持久化待解析状态（child_source_event_id + MessageSource + account_id + conversation +
  父平台消息 ID 天然在同一行表达），`replies_to` VIEW 由 `reply_to_event_id` 驱动；Backfill
  与实时共用 `insert_message_if_absent` 统一幂等入口；线程投影有 `reply_child_thread_id`
  兜底。因此**无需新表/新迁移**，全部改动收敛在 `personal-secretary-mysql` 仓储层。
- **父先子后（即时关联）**：`resolve_reply` 增加会话与来源通道过滤——父事件必须与子消息
  同 `account_id`、同 `source_channel`、同 `conversation_id`；相同平台消息 ID 出现在不同
  账号/不同群/群与私聊之间一律 fail-closed（不解析，保持 pending），绝不凭 message_id
  跨账号或跨会话串联。
- **子先父后（事务内解析）**：父事件 Accepted 入库时，`resolve_pending_replies_in_txn` 在
  同一事务内把同账号、同会话、同通道、`reply_to_event_id IS NULL` 的 pending 子事件
  幂等回填为正式关系（UPDATE 自带行锁，`IS NULL` 条件保证并发父/子 Worker 不会重复回填），
  并 DELETE 这些子事件旧的 `secretary_thread_events` 成员行与 `secretary_thread_relations`
  出边，让确定性线程投影重新处理（`claim_projection_batch` 以 `te.source_event_id IS NULL`
  领取未投影事件，复用既有游标/租约机制，不建立第二套投影状态机）。
- **Duplicate 重放**：Duplicate 父事件同样触发 `resolve_pending_replies_in_txn`，修复此前
  未完成的待解析关系；Duplicate 子/父均不新增 SourceEvent、pending、正式关系或重复派生
  （`uk_secretary_source_delivery` 与 `uk_secretary_thread_relation` 兜底）。
- **并发交错自愈**：父事件恰在子事件事务期间提交时，子事务内首次查找不可见父。子事务
  提交后 `resolve_pending_reply_after_commit` 以短事务幂等重查同作用域父事件并解析；
  失败整体回滚且可重试（消息重放为 Duplicate 后仍会再次进入本入口与父事件回填）。
- **派生顺序**：正式关系写入与 pending 状态推进、线程投影失效在同一事务提交；post-hook
  仍在事务成功后执行，事务提交前绝无派生观察。

### 目标 C：poison/InvalidData 二分隔离

  - batch 返回 InvalidData 且 len > 1：事务已回滚，按原顺序二分，左右半分别推入队列前部。

  - Database/Unavailable 错误不触发二分，以原批次整体重试（指数退避）。
