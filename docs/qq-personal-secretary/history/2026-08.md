## 2026-08-01 19:41（Asia/Shanghai）：Owner 待办完成与回复期待关闭

- 新增 `CompleteFollowUp`、`CompleteFollowUps`、`DismissResponseExpectation` 和
  `DismissResponseExpectations` 四种类型化 L2 Action。每批最多 20 个明确 ID/来源版本，
  继续复用持久化 Suspend/重启 Resume、Checkpoint 单次消费、唯一 OwnerBinding 和账号验权。
- FollowUp 完成在一个事务中执行 `scheduled -> completed`、来源版本精确加 1、due 不变，并
  压制尚未投递通知；ResponseExpectation 关闭执行 `active -> dismissed`，不伪造代表真实回复
  的 `resolved`，也不修改 EventThread/OpenQuestion。单条与批量均先锁定并验证全部目标和关联
  Outbox，再写逐目标不可变审计与整次 Effect Receipt，任一冲突整批回滚。
- 原 FollowUp MySQL 仓储已按授权、业务控制、Outbox 和审计职责拆分；回复期待控制复用同一授权
  与回执边界，不复制一套身份验证。独立复核修正四种关闭动作被错误标记为 `reversible=true`
  的产品语义并增加聚焦回归测试。6 条随机隔离 MySQL 新旧闭环、218 个领域单测、105 个服务
  单测、严格 Clippy 和 19 项应用边界检查均通过，临时 schema 已清理。未运行旧验收矩阵，未
  连接 NapCat/QQ 开放平台，也未发送 QQ 消息。

## 2026-08-01 17:44（Asia/Shanghai）：Owner 批量推迟 FollowUp

- 新增 `SnoozeFollowUps` 类型化 L2 Action，一批接受 1～20 个明确 FollowUp ID/来源版本并
  共用一个新到期时间；不同时间继续拆成多个 Action。Planner、领域门与执行用例共用目标去重、
  版本和数量约束，缺少关键字段时不从正文猜测。
- 最终 MySQL 事务按 FollowUp ID 与通知 ID 的确定顺序加锁，以数据库时钟验证新时间为未来、
  不超过 365 天且晚于所有目标当前 due。任一目标或 Outbox 不安全即整批回滚；成功时全部保持
  scheduled、due 更新、版本精确增加 1，旧 pending/failed 通知被压制，每目标写一条 snooze
  审计，整批只写一条 Effect Receipt。新 due 后各目标以新版本重新生成通知。
- 随机隔离 MySQL 分别验证批量推迟原子性与通知再生、单条推迟回归、批量忽略回归，三个临时
  schema 均已清理；Planner 聚焦测试、严格 Clippy 和 19 项应用边界测试通过。未执行旧验收
  矩阵，未连接 NapCat/QQ 开放平台，也未发送 QQ 消息。

## 2026-08-01 17:24（Asia/Shanghai）：Owner 批量忽略 FollowUp

- 新增 `DismissFollowUps` 类型化 L2 Action，一批只接受 1～20 个明确 FollowUp ID 与 Owner
  所见来源版本，重复 ID、零版本或缺失关键字段在进入数据库前拒绝；继续复用现有 Suspend、
  重启 Resume、Checkpoint CAS 和 OwnerBinding 授权边界。
- 专用 MySQL 事务按 FollowUp ID 固定顺序锁定并验证全部目标，再按通知 ID 固定顺序锁定
  legacy 与 policy-owned Outbox。任一目标已变化或存在 claimed/unknown_commit 通知即整批
  回滚；成功时全部更新为 dismissed、版本精确增加 1、压制 pending/failed 通知，并按目标写
  不可变审计、按批次写一条 Effect Receipt。审计 ID 使用无歧义字段边界稳定派生。
- 随机隔离 MySQL 分别验证批量成功与错误版本全回滚、单条忽略回归、单条推迟回归，三个临时
  schema 均已清理；Planner 两条聚焦测试、严格 Clippy 和 19 项应用边界测试通过。未执行旧
  验收矩阵，未连接 NapCat/QQ 开放平台，也未发送 QQ 消息。

## 2026-08-01 14:42（Asia/Shanghai）：Owner 推迟单个 FollowUp

- 新增 `SnoozeFollowUp` 类型化 L2 Action，显式携带 FollowUp ID、Owner 所见来源版本、新 UTC
  Unix 到期时间与原因，复用既有 Suspend/重启 Resume/Checkpoint CAS 和专用 FollowUp 控制端口。
- 最终 MySQL 事务以数据库当前时钟复验新时间晚于当前时间、晚于原 due 且不超过 365 天；锁定
  FollowUp 与 legacy/policy-owned 两类 Outbox，精确推进来源版本、压制未投递通知，并原子写入
  含前后 due/版本的不可变审计和 Effect Receipt。claimed/unknown_commit 拒绝，delivered 保留。
- 到达新 due 前不会产生新 Candidate；到达后 source_version=2 的 Candidate/Request 经统一策略
  求值生成新的 Outbox occurrence，旧 suppressed 行保持终态。独立复核发现原测试在 OwnerBinding
  建立前求值，修正 fixture 顺序后随机隔离 MySQL 完整闭环通过，临时 schema 已清理。严格
  Clippy 与 19 项应用边界测试通过；未运行旧验收矩阵，未连接或发送 QQ。

## 2026-08-01 13:45（Asia/Shanghai）：补齐 policy-owned Outbox 压制

- 复核 Task 7 后发现现行 Outbox 通过 Notification Candidate 回溯 FollowUp，行内 legacy
  `follow_up_id` 为空。控制事务现同时锁定并压制 legacy 与 policy-owned 两种 Outbox，避免
  “业务已忽略但现行通知仍待投递”。
- 聚焦 MySQL 测试不再手工插入 legacy Outbox，而是真实执行 Candidate→Evaluation→Decision→
  policy-owned Outbox 后再审批忽略；结果通过，随机 schema 已清理。

## 2026-08-01 13:38（Asia/Shanghai）：Owner 忽略单个 FollowUp

- 新增 `DismissFollowUp` 类型化 L2 Action，以稳定 FollowUp ID 和 Owner 所见来源版本执行
  `Proposal → Suspend → 重启 Resume → Effect → Receipt`，不增加旁路接口或 QQ 写能力。
- 专用 MySQL 事务复验 Action 租约、OwnerCommand、唯一有效 OwnerBinding、账号和版本；将
  scheduled 更新为 dismissed 并精确增加版本，压制 pending/failed Outbox，原子写入控制审计和
  通用回执。claimed/unknown_commit 保守拒绝，delivered 历史保留。
- 独立评审修复三处边界：FollowUp ID 收紧为 36 字节、Proposal JSON 必须与 ID/Action 一致、
  锁定 FollowUp 的全部 Outbox 行以消除检查后被投递 Worker 抢占的竞态。真实隔离 MySQL 首轮
  发现测试 SQL 使用 Rust 数字下划线，次轮发现 unsigned 版本以 i64 解码；修正后完整主路径与
  错误版本回滚通过，临时 schema 已清理。未执行 NapCat 或 QQ 开放平台实机操作。
