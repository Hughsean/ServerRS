  禁止使用真实 MemoryFactId 绕过 `fact_N`。

### MEM-004：承诺生命周期闭环

**B2 — 承诺查询**：
- 新增 `CommitmentQuery` 过滤结构（status/due 范围/promisor/beneficiary/limit）和 `CommitmentSummary` 结果类型。
- `RetrieverStoreT` 新增 `list_commitments(query)` → `Vec<CommitmentSummary>`。
- MySQL 实现：动态拼接 status/promisor/beneficiary/due 过滤 + 来源有效性交叉验证 + LEFT JOIN FollowUp 获取关联状态。
- `CommitmentStatus` 新增 `as_str()` 方法。

**B3 — 闭合 CompleteFollowUp→Commitment 一致性缺口**：
- 单条与批量 Complete 共用 `close_commitment_on_complete`；若 FollowUp 来源是承诺记忆（`reason_code = 'commitment_due'`），缺少 `source_memory_fact_id` 时 fail-closed，并在同事务内：
  1. `FOR UPDATE` 锁定来源 Commitment Fact（必须是 confirmed 状态）。
  2. 校验 commitment 仍为 Pending（已被并发 Effect 关闭则跳过，FollowUp 仍正常完成）。
  3. 旧 Pending Fact → superseded（CAS: `fact_status = 'confirmed'`）。
  4. 插入新 Confirmed Fulfilled Commitment Fact（复用旧事实的 subject_key/confidence/sources；`completion_source_event_id` 指向本次授权 OwnerCommand；`supersedes_fact_id` 指回旧 fact_id）。
  5. 复制来源引用 + 追加 `completion_source_event_id` 到来源列表。
  6. 任一失败全部回滚（调用方已在事务内）。
- Dismiss/Snooze 只影响提醒行为，不修改承诺语义状态（保持不变）。
- 相同 effect_id + proposal_id 重放返回既有 Receipt，不重复创建 Fulfilled Fact；错误版本和错误批量均整体回滚。
